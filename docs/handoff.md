## Продукт и согласованный объём

**Следующий этап согласован 7 октября 2026:** см. [product-plan.md](product-plan.md).
Там зафиксированы команды до проекта, события, сообщества с участниками и
публикациями, открытый набор источников и четыре сочетания оформления/темы.
Это целевой план; описание ниже относится к реализации v0.1. Коралловый
концепт реализован в светлой и тёмной темах, функциональные изменения
ещё не начаты. Монохром остаётся следующим отдельным оформлением.

Krug — сеть вокруг проектов, людей и совместной работы. Внешние источники решают cold start, но не являются конечной ценностью. Основной путь: discovery → intent/Interested → люди/роли → участие → project updates. GitHub — один bootstrap-источник, не ядро продукта. Синяя палитра заменена согласованным тёплым коралловым оформлением; сохраняется native HTML/CSS/JS без сборщика.

В последнем согласованном объёме есть native/imported/claimed проекты, ручные submissions и admin review; Save/Follow/Interested с отдельным согласием на публичный интерес; opt-in intent-профиль, люди и открытые роли; заявки/accept/reject, участники и закрытый контакт после принятия; публичные project/update страницы и OpenGraph. Старая social-функциональность вторична. Не добавлять chat, управление задачами, ML matching, billing или federation.

## Состояние реализации

Коралловая версия проверена 7 октября 2026 на изолированном Fedora preview. Состояние основного сервера и точный коммит будут сверены после развёртывания. Поиск расположен над выдачей, фильтры — в боковой панели на desktop и в сворачиваемом блоке на телефоне; «Всё» показывает смешанную сетку реальных проектов, ролей и людей. Обложек проектов в модели нет, поэтому декоративные изображения концепта не добавлялись. Монохром и функциональное расширение остаются планом.

Native Krug уже существует. Его владелец ведёт dev blog самостоятельно: не создавать вымышленные updates от его имени. Команды уже включены последующим запросом пользователя; раннее решение «без заявок» больше не определяет текущий объём.

Используется modular monolith FastAPI/async SQLAlchemy/PostgreSQL/Alembic, существующие Celery/Redis для фоновой работы и native frontend. Миграция приложения: `c4e8d1a9b210`. Сохранять auth, signed cursors, PostgreSQL search, permissions, media validation и outbox; не переписывать историю миграций и не сбрасывать БД повторно.

## Проверки и оставшиеся ограничения

На изолированном Fedora preview: **270 Python-тестов прошли**, JS syntax/i18n/header/likes и diff checks прошли. Backend не менялся, новых миграций нет.

Единый `browser_collaboration.cjs` прошёл: создание проекта, intent, private/public Interested, Save/Follow, заявка, acceptance, контакт, membership и member update. Admin submission/claim в этом прогоне пропущены; их прежние отдельные проверки не считаются новым полным admin E2E.

`browser_discovery_viewports.cjs` прошёл на 320–3840 CSS px: RU/EN, светлая/тёмная тема, фильтрация, resize, клавиатура, reduced-motion, отсутствие View Transition API, быстрые переключения темы и частичная ошибка 503. System theme отдельно проверена с изменением системной цветовой схемы. Скриншоты мобильной/desktop/2K/4K композиции просмотрены; это эмуляция viewport, не физические устройства. Намеренная отмена анимации не оставляет необработанный `ViewTransition.ready` rejection.

Публичного домена пока нет. Видео, events/community search, alerts и широкий внешний supply не реализованы. Не путать GitHub collector с поиском по всему интернету. Следующий продуктовый шаг — личная проверка пользователя и его первый настоящий update, затем исправления по обратной связи.

## Работа агента

Следовать актуальному глобальному `AGENTS.md` и `astra-orchestrator`: root Sol medium принимает решения и проверяет; Luna medium пишет код/тесты/скрипты. Выбирать Luna-роль с `fork_turns="none"`; generic defaults не гарантируют модель при полном fork. Не превращать Sol-аудитора в исполнителя.

До делегирования распределить файлы; один владелец каждой области и браузерной сессии. Передавать краткий контракт. Не повторять полный аудит исполнителя, не отправлять регулярные status pings. Повторять проверки при изменениях, сбоях и незакрытых рисках, указывая состояние кода и окружение. Обязательные security, responsive, Fedora и документационные проверки сохраняются.

Для Fedora использовать команды проекта из `docs/development.md`; сохранять `.env`, секреты, media, рабочие volumes и backups. Проверять чистоту checkout перед обновлением. Подробности доступа и пароли не переносить в Git или handoff.
