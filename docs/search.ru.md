# Мультиязычный поиск в блоге

[English version](search.md)

## Что реализовано

Поиск в `GET /posts` теперь проверяет заголовок и содержимое постов текущего пользователя. Используется PostgreSQL Full Text Search (FTS), сохраняемые вычисляемые колонки `tsvector` и GIN-индексы. Результаты упорядочены по релевантности, затем по дате создания и ID. Формат ответа не изменился: `items`, `next_cursor`, `has_more`.

Также восстановлены две функции в `backend/crud/posts.py`: получение опубликованного поста и списка постов автора. Раньше внутри незавершённого `db.execute(` находились параметры отсутствующего объявления следующей функции. Это была синтаксическая ошибка, мешающая импорту приложения.

`GET /posts` ищет **свои записи** после входа, а `GET /explore` публично ищет опубликованные записи всех авторов. Оба используют одинаковые FTS-режимы. Поиск в ленту подписок не добавлен. Права доступа и фильтры сохраняются. Язык поиска не связан с RU/EN языком интерфейса или аккаунта.

## Архитектурное решение: явный язык запроса

Параметр `search_language` принимает три значения:

| Значение | Поведение | Пример |
|---|---|---|
| `simple` (по умолчанию) | Поиск токенов без морфологии, с приведением регистра | `dunyo` находит `Dunyo` |
| `russian` | Русский стемминг и стоп-слова | `кошка` находит `кошки` |
| `english` | Английский стемминг и стоп-слова | `run` находит `running` |

Стемминг — приведение слов к поисковой основе. Это не полноценное понимание смысла или грамматики.

Почему язык задаётся явно? Короткие запросы вроде `go` неоднозначны: это может быть слово, название языка программирования или часть другого языка. Определение языка по алфавиту также не различает английский и узбекский на латинице. Явный параметр даёт предсказуемый результат без дополнительной библиотеки или сервиса.

`simple` подходит для смешанного текста и языков без настроенной морфологии. Например, запрос `Python PostgreSQL` найдёт документ `Python и PostgreSQL`. Однако это **не универсальная поддержка морфологии всех языков**: узбекские окончания, транслитерация, варианты апострофов, удаление акцентов и сегментация китайского/японского текста специально не реализованы. Токенизация остаётся стандартной PostgreSQL.

Для русско-английского смешанного текста `simple` сохраняет точные слова обоих языков. Один запрос в режиме `russian` не включает одновременно английский стемминг. Автоматическое объединение результатов нескольких языковых режимов сознательно не вводилось: оно усложняет ранжирование, фразы и пагинацию.

## Почему три вектора

Каждый пост хранит три поисковых представления:

```text
posts
├── title / content          исходный текст
├── search_simple           нейтральное представление
├── search_russian          русские поисковые основы
└── search_english          английские поисковые основы
```

У каждого представления свой GIN-индекс. В запросе выбирается одна заранее разрешённая колонка, соответствующая `search_language`. Имя колонки не строится из произвольного пользовательского текста.

Это расходует больше места и требует трёх вычислений при записи. Зато каждый запрос использует согласованную пару «конфигурация документа — конфигурация запроса», включая фразы и исключения. Нет трёх параллельных поисков и сложного слияния оценок.

Альтернатива — хранить язык каждого поста и один вектор. Она экономнее, но требует определять язык при записи, классифицировать старые записи и решать, что делать со смешанным текстом. Для текущего API выбраны три фиксированных режима без изменения формы создания поста. Если понадобятся десятки языков, эту стратегию стоит пересмотреть, а не добавлять десятки колонок.

## Как текст становится поисковым документом

Для русского режима выражение выглядит так:

```sql
setweight(
    to_tsvector('pg_catalog.russian'::regconfig, coalesce(title, '')),
    'A'
)
||
setweight(
    to_tsvector('pg_catalog.russian'::regconfig, coalesce(content, '')),
    'B'
)
```

- `to_tsvector` разбирает текст на поисковые лексемы.
- `coalesce` заменяет `NULL` пустой строкой.
- `setweight` помечает важность источника слова.
- `A` у заголовка имеет больший стандартный вес, чем `B` у содержимого.
- `||` объединяет два представления в один документ.

При прочих равных совпадение в заголовке получает более высокую оценку. Это не абсолютное правило «все заголовки всегда выше любого содержимого»: на `ts_rank` влияет и число совпадений.

Вектор объявлен через `Computed(..., persisted=True)`, то есть `GENERATED ALWAYS AS (...) STORED`. PostgreSQL сам пересчитывает его при изменении текста, включая прямой SQL. Поэтому в `create_post` и `update_post` нет ручной синхронизации индекса. При добавлении колонки старые записи тоже получают вектор.

Колонки помечены `deferred` в SQLAlchemy: обычное чтение постов не загружает их содержимое. Они нужны базе для поиска, но не должны попадать в JSON API.

## Что делает GIN

Упрощённо индекс содержит соответствия:

```text
python → посты 10, 20, 35
поиск  → посты 20, 42
```

Он ускоряет отбор совпадений через `@@`. Он не хранит готовую сортировку по релевантности: релевантность зависит от конкретного запроса. PostgreSQL вычисляет оценку найденным строкам и сортирует их отдельно. Для очень частого слова кандидатов может быть много, поэтому наличие индекса не гарантирует одинаково быстрый ответ на любой запрос.

## Как выглядит запрос

Упрощённый SQL первой страницы:

```sql
SELECT id, title, content,
       ts_rank(
           search_russian,
           websearch_to_tsquery('pg_catalog.russian', 'кошка')
       )::double precision AS rank
FROM posts
WHERE author_id = 42
  AND search_russian @@ websearch_to_tsquery('pg_catalog.russian', 'кошка')
ORDER BY rank DESC, created_at DESC, id DESC
LIMIT 21;
```

При размере страницы 20 запрашивается 21 строка: дополнительная строка показывает, есть ли следующая страница. Полный `COUNT(*)` не нужен.

В приложении текст передаётся параметром SQLAlchemy. Пользовательская строка не вставляется в SQL конкатенацией. Режим проверяет Pydantic через `Literal`, неизвестный язык возвращает 422.

`websearch_to_tsquery` позволяет использовать:

| Запрос | Условие |
|---|---|
| `python postgres` | Оба слова |
| `python OR postgres` | Любое из слов |
| `"red green"` | Фраза |
| `python -django` | Python без Django |

Поисковым документом считается объединение заголовка и содержимого; фразы не ограничены одним полем. Стандартные ограничения позиций PostgreSQL сохраняются, особенно для очень длинных текстов.

## Поведение API и примеры

Для `/posts` требуется заголовок авторизации; `/explore` доступен без входа и исключает черновики. В примерах URL показаны для чтения; клиент должен корректно кодировать пробелы, кавычки и кириллицу.

```http
GET /explore?search=кошка&search_language=russian&limit=20
GET /posts?search=кошка&search_language=russian&limit=20
GET /posts?search=run&search_language=english&is_published=true
GET /posts?search=dunyo
GET /posts?search=Python%20PostgreSQL&search_language=simple
```

Без `search` или с одними пробелами возвращается обычная хронологическая страница. Краевые пробелы обрезаются. Строка из пунктуации и запрос из одних стоп-слов выбранного языка дают пустую поисковую выдачу; они не превращаются в «покажи всё».

Максимальная длина запроса остаётся 100 символов. `limit` — от 1 до 100. `search_language` без текста поиска не меняет обычный список.

Пример ответа (поля поста сокращены):

```json
{
  "items": [{"id": 42, "title": "Кошки"}],
  "next_cursor": "opaque-signed-token",
  "has_more": true
}
```

На следующей странице передавай тот же запрос, язык и фильтр публикации, добавляя `cursor`. Размер страницы можно менять.

Старый поиск `ILIKE '%кот%'` мог находить «котлован». FTS ищет слова/основы, а не произвольные подстроки. Поэтому переход меняет семантику поиска, а не только скорость. Старые поисковые курсоры становятся недействительными; курсоры обычных списков продолжают работать.

## Зачем менялась пагинация

Раньше курсор содержал только дату и ID. Но теперь старый пост с высоким рейтингом может предшествовать новому посту с низким рейтингом:

| Пост | rank | Дата |
|---|---:|---|
| A | 0.9 | 1 сентября |
| B | 0.5 | 15 сентября |

Если после A выбирать только записи старше 1 сентября, B потеряется. Поэтому поисковый курсор хранит `(rank, created_at, id)` и продолжает тот же порядок:

```sql
WHERE (rank, created_at, id) < (:rank, :created_at, :id)
ORDER BY rank DESC, created_at DESC, id DESC
```

Вычисленный `rank` приводится к double precision до сортировки и сравнения. Python/JSON сохраняет его без ручного округления. Это помогает точно воспроизвести границу страницы; равенство рангов разрешается датой и ID.

К существующему `Cursor` добавлено необязательное поле `rank`, а декодирование проверяет режим курсора. Подпись HMAC и проверка области действия остаются общими. Область поискового курсора включает пользователя, запрос, язык, фильтр публикации и версию поисковой логики `posts_search_v1`.

Так избегаем второй почти идентичной реализации криптографической подписи. При этом обычный курсор нельзя использовать для поиска и наоборот.

Страницы не являются снимком базы: изменение текста может изменить rank и переместить запись через границу. Удаление граничной записи само по себе не ломает следующую страницу — её значения уже сохранены в курсоре. Для строгого снимка нужна отдельная архитектура поисковой сессии; здесь её нет.

## Почему пока нет pg_trgm

FTS не исправляет опечатки. Запрос `pyhton` не обязан найти `python`.

`pg_trgm` добавляет другой вид совпадения: сходство фрагментов строки. Чтобы использовать его качественно, нужно определить порог сходства, сравнение слова с длинным заголовком, порядок смешивания с FTS и правила курсора. Это отдельное поведение, а не обязательная часть FTS.

В исходной задаче расширение было условным. Оно не добавлено без требования к качеству исправления опечаток: так остаётся один понятный алгоритм выдачи. Следующий осмысленный шаг — отдельный режим похожих заголовков с собственными тестами и замерами.

Миграция намеренно содержит собственное выражение вектора, а не импортирует функцию из модели: старая миграция должна оставаться воспроизводимой после изменения приложения.

## Применение миграции

```bash
.venv/bin/alembic upgrade head
```

`scripts/start` применяет миграции новым образом до запуска web/worker/beat. На большой работающей базе сохраняемые колонки требуют обработки существующих строк, а обычное создание GIN блокирует запись. Эту миграцию следует выполнять в согласованное окно обслуживания. Она выбрана для текущего небольшого проекта; это не схема обновления огромной базы без простоя.

`downgrade` удаляет только поисковые индексы и колонки, сохраняя исходные посты. Старую версию приложения следует запускать со схемой, которую она ожидает.

## Проверки и воспроизведение

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m scripts.explain_search
```

Тесты используют отдельную `test_db`. Проверены поиск в содержимом, смешанный текст, русский/английский стемминг, приоритет заголовка, равные оценки, переходы через границы дат, удаление граничного поста, чужие посты, фильтр публикации, смена языка курсора, обновление вектора через API и прямой SQL, пустые результаты и синтаксис websearch.

Скрипт замера создаёт временную таблицу `posts` по схеме настоящей, включая вычисляемые колонки и индексы. Она видна только его соединению. Заполняет 30 000 синтетических постов, обновляет статистику и выполняет `EXPLAIN (ANALYZE, BUFFERS)` для редких и частых слов. Затем откатывает транзакцию. Исходные посты не меняются. Разрешена только база с именем `test_db`.

Сравнение с ILIKE иллюстрирует стоимость двух запросов на этом наборе. Семантика и сортировка различаются, поэтому это не доказательство универсального коэффициента ускорения.

## Фактические результаты EXPLAIN ANALYZE

Замер выполнен 20 сентября 2026 года на локальном PostgreSQL, во временной таблице с 30 000 постов и 30 авторами. У выбранного автора 1000 постов; редкий термин встречается в 50 из них (150 во всей таблице). Данные синтетические, каждый текст содержит повторяющийся абзац. Индексы не отключались, план выбирал PostgreSQL.

| Запрос | Execution Time | Способ отбора |
|---|---:|---|
| `ILIKE` по title/content, `quartz` | 39.782 мс | Индекс автора, проверка текста 1000 строк |
| FTS `simple`, `quartz` | 20.210 мс | Пересечение индекса автора и GIN |
| FTS `russian`, `кошка` | 17.923 мс | Пересечение индекса автора и GIN |
| FTS `english`, `run` | 17.228 мс | Пересечение индекса автора и GIN |
| FTS `simple`, частое `common` | 10.866 мс | Индекс автора, проверка вектора 1000 строк |

Сокращённый реальный план для `simple/quartz`:

```text
Limit
  -> Sort
       Sort Key: ts_rank(...) DESC, created_at DESC, id DESC
       Sort Method: top-N heapsort
       -> Bitmap Heap Scan on posts
            Heap Blocks: exact=50
            -> BitmapAnd
                 -> Bitmap Index Scan on posts_author_id_is_published_created_at_id_idx
                      Index Cond: (author_id = 1)
                 -> Bitmap Index Scan on posts_search_simple_idx
                      Index Cond: (search_simple @@ '''quartz'''::tsquery)
Execution Time: 20.210 ms
```

Имена индексов временной копии генерирует PostgreSQL; в основной схеме соответствующий индекс называется `ix_posts_search_simple`.

Главный подтверждённый результат — GIN действительно участвует в поиске, а для редкого термина читаются 50 блоков таблицы вместо 1000. Частый термин PostgreSQL проверяет после отбора автора, поскольку GIN для слова, присутствующего во всех постах, мало помогает.

Это один последовательный прогон, без выравнивания состояния кэша, с отличающимися полями SELECT и сортировкой у baseline. В частности, меньшая задержка частого слова не означает, что частые запросы всегда быстрее редких. Числа зависят от кэша, нагрузки, pending list GIN и распределения данных. На рабочей базе измерения нужно повторить с настоящими запросами.
